# JobPilot · 投递参谋

> 一个面向「AI 应用开发 / Agent 开发实习」求职者的岗位匹配与投递决策 Agent。

---

## 一、背景：为什么做这个

### 1.1 我自己的真实处境

我在冲 2026 年 12 月末前拿到第一段 AI Agent 技术实习。按计划，12 月中开始每天投 20–30 家，到明年 6 月前累计会接触 200+ 个岗位。

这个量级下，靠人肉的三个动作全部失效：

| 动作 | 人肉做法 | 为什么失效 |
|---|---|---|
| 读 JD | 一家一家点开看 | 200 份 JD，每份 800 字，读不完；读完也记不住 |
| 判断匹配 | 凭感觉「这个我行」 | 没有统一标准，越投越焦虑，容易投一堆自己根本够不上的 |
| 决定补什么 | 看到什么缺什么 | 关键词散落在 200 份 JD 里，人脑做不了聚合 |

更关键的是：**我不知道自己缺的是「工程深度」还是「关键词」**。这直接决定我是该继续打磨项目，还是该补某个具体技术点。

### 1.2 要解决的核心问题

> 把 200 份散落的 JD 变成一个能回答问题的知识库：
> **「以我现在的简历，哪些岗位值得投？我离它们差什么？差的那部分，市场上有多少岗位真的在要？」**

### 1.3 三个具体用户故事（这就是验收标准）

1. **筛岗**：「上海/杭州、AI Agent 方向、接受实习的岗位里，哪些和我简历的重合度最高？给我前 10 个，并说明每个为什么匹配。」
2. **补短板**：「我简历里没有 LangGraph，这个技能在我要投的岗位里出现了多少次？是硬性要求还是加分项？」
3. **公司尽调**：「这家公司是套壳还是真有工程链路？JD 里有没有出现 RAG / 向量库 / 评估 / 线上部署 这类词？」——对应「反背调」筛选逻辑，把公司分成「核心岗 / 边缘应用层 / 套壳」。

### 1.4 为什么这个场景适合练 Agent，而不是套壳聊天

面试官最烦「又一个 ChatGPT 套壳」。这个项目能站住，是因为它天然需要 Agent 的四件套：

- **需要 RAG**：200 份 JD 无法塞进 context，必须切分 + 向量检索，「哪些岗位要求 LangGraph」这种问题只能靠语义检索回答。
- **需要 Tool Calling**：简历是本地文件、岗位在库里、统计要跑 SQL，这些都不是 LLM 自己能算的，必须封成工具。
- **需要多步编排（LangGraph）**：用户一句话背后意图不同（找岗位 / 问差距 / 查公司），要先路由，再决定调检索还是调打分，还要能「检索不到就放宽条件重查」。
- **有明确的可评估标准**：匹配分对不对，可以拿人工标注的 golden set 来量。这是最稀缺的东西——**大部分 Agent 项目根本没法证明自己有效**。

### 1.5 为什么不是别的场景

- 通用文档问答 / 聊天机器人：无业务闭环，无评估标准，面试一问「你这个比 ChatGPT 强在哪」就死。
- 合同条款问答：拿不到真实语料。
- 电商客服 / 工单：语料和业务规则都编不出来，讲不深。

而这个场景的语料**我自己就能生产**：投递过程中看到的 JD，手动整理成 JSON 即可，不爬站、不违规。而且到了 12 月中我真的天天要用它 → 有真实用户（我自己）→ 有真实反馈 → 有真实迭代故事。

## 二、边界：做什么，不做什么

**做（MVP 范围）**
- 岗位库：结构化存储 JD（公司/岗位/城市/薪资/全文/技能标签/来源）
- 检索：按语义找岗位，按技能反查岗位
- 匹配：简历 vs 岗位，给出分数 + 差距项 + 理由
- 尽调：从 JD 文本判断岗位「含金量」（核心研发 / 边缘应用 / 套壳）
- 可追溯：每个结论必须能指回具体 JD 原文（防幻觉）

**不做（明确砍掉，避免摊大）**
- ❌ 不做自动投递 / 自动打招呼（合规风险 + 平台风控，且对面试无加分）
- ❌ 不做简历生成 / 简历美化（另一个产品了）
- ❌ 不做多用户、不做登录、不做前端美化（最多一个 Streamlit / 单页 HTML）
- ❌ 不做爬虫（数据手动/半手动整理，够 200 条即可）

## 三、路线图：每一周往上叠一层

| 阶段 | 加的能力 | 对应冲刺周 |
|---|---|---|
| v0.1 | JD 入库 + 关键词检索（SQL LIKE） | W1 |
| v0.2 | 向量检索（RAG）：切分 / embedding / top-k / 引用来源 | W2 |
| v0.3 | LangGraph 编排：意图路由 → 检索/工具 → 打分 → 自检补检索 | W3 |
| v0.4 | 工程化：会话记忆、工具失败降级、重试、Token/延迟日志、Docker | W4 |
| v0.5 | 评估：golden set 回归、匹配分准确率、幻觉率 | W4–W5 |

> 注意演进逻辑：**先 SQL 后向量**、**先裸 ReAct 后 LangGraph**。每一步都是因为上一步不够用才升级——这个「为什么升级」就是面试时最有说服力的部分。

## 四、技术栈（锁版本，不要中途换）

- Python 3.11+
- FastAPI + Pydantic v2 + uvicorn（服务层）
- SQLite + SQLAlchemy 2.x（存储，够用且零部署）
- LLM：OpenAI 兼容接口（DeepSeek / 通义 / OpenAI 均可，靠 `OPENAI_BASE_URL` 切换）
- 向量库：chromadb（本地持久化，W2 引入）
- 编排：langgraph（W3 引入）
- 其他：python-dotenv、requests、pytest

## 五、数据结构

```
jobs                岗位主表
  id, company, title, city, salary, jd_text, source, url, created_at

job_skills          岗位-技能（由 LLM 从 JD 抽取）
  id, job_id, skill, category, is_required   -- category: 语言/框架/AI/工程/软技能
                                             -- is_required: 硬性 vs 加分

resumes             简历（先只支持一份，纯文本）
  id, name, content, updated_at

applications        投递记录（W4 起用）
  id, job_id, applied_at, status, note
  -- status: 待投 / 已投 / 已读 / 约面 / 面试中 / 挂 / offer

doc_chunks          RAG 用（W2 引入）
  id, job_id, chunk_text, embedding, meta
```

## 六、怎么知道它好使（评估）

**这是整个项目最值钱的部分，别跳过。**

1. **Golden set**：挑 20 条 JD × 1 份简历，人工标注匹配度三档（高/中/低）。存成 `eval/golden.json`。
2. **指标**：
   - 匹配分与人工标注的一致率（三档分类准确率）
   - Top-10 推荐里人工认为「值得投」的比例
   - 幻觉率：结论中无法指回原文的比例（目标 0）
   - 平均延迟、平均 Token 消耗
3. **回归**：每次改 prompt / 换模型 / 换检索策略，跑一遍 golden set 看涨没涨。

> 面试话术：「我没有只看它跑通没，我建了 20 条人工标注的评测集，改 prompt 前后准确率从 X 到 Y。」——绝大多数候选人没有这一句。

## 七、本地运行

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt

copy .env.example .env          # 填入 API Key
python scripts/load_jobs.py     # 导入 data/jobs.json 到 SQLite
python scripts/check_llm.py     # 验证 LLM 连通性
```

## 九、合规与数据来源说明

- 所有 JD 均为**手动整理**的公开岗位描述片段，仅用于个人学习与检索演示，不包含公司内部信息。
- 不实现爬虫、不绕过任何平台限制。
- 仓库公开前会检查是否含真实姓名、联系方式、简历原文等个人信息。
